# Точка доступа к хранилищам базы

Язык: **Русский** | [English](../en/StorageAccessPoint.md)

## Назначение и первое подключение

Точка доступа открывает несколько существующих хранилищ в одном окне. Предметы остаются в исходных инвентарях: отдельная объединённая коллекция не создаётся. Это удобно для склада базы, где игроку нужен доступ сразу к нескольким сундукам или полкам.

Перед подключением подготовьте обычный инвентарь игрока, HUD и управление по [руководству интеграции](ProjectIntegration.md) и [настройке ввода](InputConfiguration.md).

Для первого примера:

1. Разместите два контейнера с `ContainerComponent` и `InventoryCollectionComponent`. Задайте каждому `StartupInventories`, название `ContainerTitle`, классы интерфейса и стартовое содержимое. Для сеток, создаваемых без готового UI, используйте `bCollectInvDataFromWidget = false` и задайте размеры и классы слотов.
2. Разместите `BP_StorageAccessPoint` из папки примеров `Blueprints/Examples/Storage`. Проверьте, что его меш блокирует канал взаимодействия персонажа.
3. В `StorageAccess` выберите `DiscoveryMode = Explicit` и добавьте оба актора в `ExplicitContainers`. Это позволяет сначала проверить состав склада без настройки автоматического поиска.
4. Проверьте `WindowClass`: должен быть назначен виджет `WBP_StorageAccess`. Задайте понятный `WindowTitle`, например «Склад базы».
5. Назначьте `MaxUseDistance` и согласуйте его с глобальным `MaxInteractionDistance` в общих настройках. Оба ограничения участвуют в доступе; радиус поиска контейнеров задаётся отдельно.
6. Запустите игру, подойдите к точке и используйте обычное основное взаимодействие. В окне должны появиться два хранилища и инвентарь игрока. Проверьте перенос, поиск по названию, закрытие и повторное открытие.

Не задавайте одинаковый `CustomInventoryID` независимым инвентарям. Если специальный ID не нужен, оставьте его пустым для автоматического создания.

## Автоматический поиск и права доступа

Для склада, который расширяется новыми сундуками, выберите Radius или RadiusAndExplicit. `SearchRadius` измеряется от точки доступа до акторов контейнеров. Например, 2000 см соответствует 20 метрам. Это радиус обнаружения хранилищ, а не допустимая дистанция игрока от стойки.

Для отбора одной базы можно задать `RequiredActorTag`, например `Base_A`, и добавить такой же обычный Actor Tag нужным контейнерам. `RequiredInventoryTag` — отдельный Gameplay Tag инвентаря. Эти два поля используют разные системы тегов. Явные записи обходят фильтры автоматического поиска, поэтому добавляйте в них только нужные источники.

Принадлежность к базе или команде проверяйте в Blueprint-переопределении `CanPlayerAccess`: верните true только для разрешённых игроков. Сам по себе `RequiredActorTag` выбирает контейнеры и не ограничивает круг игроков. По умолчанию точка допускает любого действительного игрока, прошедшего проверку расстояния.

После создания нового контейнера во время игры вызовите `RefreshContainers` либо `AddContainer` на сервере. Для динамического явного добавления выберите Explicit или RadiusAndExplicit. Поиск в строке окна меняет только видимость панелей, а не состав разрешённого доступа.

## Проверка после настройки

Проверьте добавление и удаление контейнера, выход игрока за дистанцию и отказ `CanPlayerAccess`. Для сетевой игры дополнительно проверьте два одновременных сеанса: перенос должен менять исходное содержимое, а закрытие одного окна не должно прекращать доступ второго игрока. Это сценарии проверки целевого проекта; в рамках обновления документации они заново не запускались.

Общее окно склада и доступ к снаряжению NPC настраиваются отдельно. Для второго сценария используйте [манекен и обмен с персонажем](CharacterInventoryExchange.md).

На уровень можно перетащить `BP_StorageAccessPoint` из
`InventorySystemInvenzaPlugin/Blueprints/Examples/Storage`.
Это обычный объект взаимодействия: у него есть меш и `StorageAccess`.
Меш можно заменить своим. Окно открывается существующей клавишей взаимодействия;
закрывается кнопкой Close, Escape или клавишей инвентаря.

## Настройка StorageAccess

- `DiscoveryMode`: Radius — поиск по радиусу; Explicit — только явно заданные;
  RadiusAndExplicit — оба источника.
- `SearchRadius`: радиус в сантиметрах. Автоматически находятся акторы с
  `UContainerComponent` и их инвентари из `UInventoryCollectionComponent`.
- `RequiredActorTag`, `RequiredInventoryTag`: необязательные фильтры автоматического поиска.
  Явно добавленные контейнеры/инвентари обходят эти фильтры и радиус.
- `ExplicitContainers`: список акторов на уровне.
- `ExcludedInventoryNames`: чёрный список названий `ContainerTitle` (если пустое — ID
  инвентаря). Полное совпадение без учёта регистра и пробелов по краям; пустые строки
  игнорируются. Действует во всех режимах, включая явное добавление. Переопределение
  `DisplayName` не меняет результат проверки. После изменения списка на сервере
  во время игры вызовите `RefreshContainers`.
- `MaxUseDistance`: максимальная дистанция игрока до точки доступа для открытия и операций.
- `WindowClass`: `WBP_StorageAccess` (у готового Blueprint уже задан).
- `WindowTitle`: заголовок окна.
- `CanPlayerAccess`: Blueprint-переопределение для проверки владельца базы, команды и разрешений.
  По умолчанию допускается любой игрок в пределах дистанции.

Вызовы `AddContainer`, `RemoveContainer`, `AddInventory`, `RemoveInventory`,
`ClearExclusions` и `RefreshContainers` выполняются **на сервере**.
Для динамических явных добавлений используйте Explicit или RadiusAndExplicit.
Удаление исключает контейнер/инвентарь и из дальнейших результатов автоматического поиска.
`ClearExclusions` снимает исключения от RemoveContainer/RemoveInventory и обновляет список;
настроенный чёрный список `ExcludedInventoryNames` сохраняется.
`AddContainer` снимает исключение актора; индивидуальные исключения его инвентарей остаются.
Для индивидуальной записи `FStorageInventoryEntry` можно задать DisplayName и SortOrder.
Если название не задано, используется ContainerTitle, затем ID инвентаря.

Радиус сканируется при открытии и по кнопке Refresh / вызову RefreshContainers.
Создание нового сундука или перемещение существующего требует Refresh либо AddContainer.
Изменения состава инвентарей и уничтожение уже подключённых сундуков отслеживаются событиями.
Проверок списка на Tick нет.

## Общий виджет

`WBP_InventoryWorkspace` находится в `UI/Inventory/Workspace` и используется также
в `WBP_CraftDashboard`. Слева — прокручиваемый список инвентарей, справа — инвентарь игрока.

В `WBP_StorageAccess` → **Class Defaults → Storage Access → Workspace** доступны
`Workspace Settings`:

- `Player Column Min Width` — минимальная ширина колонки игрока, по умолчанию 430.
- `Fit Player Column To Content` — расширять колонку по полному размеру контейнера,
  включая панель операций и место для вертикальной прокрутки.
- `Allow Inventory Collapse` — сворачивать хранилища нажатием на заголовок со стрелкой.
- `Hide Inventory Close Buttons` — временно скрывать крестики у всех вложенных
  контейнеров, включая инвентарь игрока справа.

При поиске, Refresh и перестроении списка сохраняется свёрнутое состояние
имеющихся контейнеров. Сворачивание скрывает только тело виджета и не меняет
содержимое или доступность инвентаря. При выходе из общего окна прежняя настройка
крестика восстанавливается. Новое окно начинает со всех развёрнутых хранилищ.

Общий `UInventoryWorkspaceWidget` принимает эти параметры через `ConfigureWorkspace`.
Его стандартные настройки оставляют сворачивание и скрытие крестиков выключенными;
режим общего хранилища включает их через `UStorageAccessWidget`.
Строка Find storage by name ищет часть **названия инвентаря**, без учёта регистра;
это не поиск названий предметов. Поиск скрывает панели без пересоздания инвентарей.
Кнопка Clear снимает фильтр. Название секции крафта — Resources, Fuel, Output.

Настройки оформления лежат в Blueprint этих виджетов и их экземплярах Core-элементов.
Скрипт создания `Scripts/UI/create_storage_workspace.py` использует палитру существующего
меню крафта. Глобальные Core-кнопки не изменяются.

## Меш точки доступа

`BP_StorageAccessPoint` использует `SM_StorageAccessDesk` — простую деревянную стойку
кладовщика с наклонной столешницей, журналом и ключами. Размер около 80 × 55 × 110 см,
1720 треугольников, одна выпуклая коллизия для движения и трассировки взаимодействия.

Меш и пять однотонных материалов: `/InventorySystemInvenzaPlugin/Meshes/StorageAccess`.
Цвета, шероховатость и металличность задаются константами соответствующих материалов.
Исходник Blender, FBX и скрипт построения лежат в `ArtSource/StorageAccess/`.

Масштаб компонента Mesh в Blueprint равен `(1, 1, 1)`. Pivot расположен на 50 см выше
основания, как у прежнего куба, чтобы сохранить высоту размещённых экземпляров.
В тестовой карте существующий экземпляр наследует новый меш и единичный масштаб
из Blueprint без изменения файла уровня. При ручном размещении основание находится
на 50 см ниже pivot; можно использовать привязку к поверхности.

Импорт: `Scripts/Storage/import_storage_access_desk.py`, запуск через
`-ExecutePythonScript` обычного Unreal Editor. Сохраняются только новый меш,
его материалы и `BP_StorageAccessPoint`. Проверка трассировки и снимок из карты:
`Scripts/Storage/preview_storage_access_desk.py`.

## Переносы и сеть

Работают переносы между показанными инвентарями и игроком, кнопки Take all / Place all /
Place matching и сортировка через принадлежащий игроку компонент.
Состав доступного сеанса реплицируется только владельцу UIInventoryManager.
Сервер повторно проверяет членство инвентаря и разрешение/дистанцию точки доступа при переносе.
Поиск не меняет эти разрешения. После удаления записи или закрытия окна доступ отзывается.
Объекты предметов и содержимое сундуков не копируются в отдельный виртуальный инвентарь.

Для удалённых явных контейнеров необходимо включить репликацию актора и его коллекции.
Пока окно открыто, задействованные акторы временно становятся Always Relevant, чтобы
удалённый клиент получил настоящие инвентари и предметы. Это расширяет репликацию для всех
соединений, а не только смотрящего игрока; для очень больших баз следует учитывать сетевой трафик.
Исходное значение восстанавливается после последнего открытого сеанса. Владение сундуками
не передаётся игроку. Список явных динамических добавлений не сохраняется автоматически в save game.

Проверки: `Invenza.Inventory.StorageAccess`, `Invenza.Inventory.StorageWorkspace`,
`Invenza.Inventory.TransferMatchingItems`, `Invenza.Inventory.StorageShutdown`.
Последняя проверка открывает общее хранилище в PIE и завершает PIE с открытым окном.
При обычном закрытии инвентарь игрока возвращается в HUD; при завершении игры
ссылки и подписки освобождаются без повторной перерисовки.

Исторические имена автотестов относятся к проверкам, исходники которых удалены по запросу владельца. В текущей поставке их нет; используйте описанные ручные сценарии.
