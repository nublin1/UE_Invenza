# Связанные общие и личные сундуки

Связанные сундуки открывают отдельный физический инвентарь, который существует
в постоянном уровне мира независимо от точек доступа. Предметы не копируются
между сундуками. Выгрузка участка карты или уничтожение сундука сохраняют вещи.

## Готовые примеры

Папка `Blueprints/Examples/Storage/Linked` содержит:

- `BP_LinkedStorageChest` — общий базовый Blueprint с существующей моделью сундука.
- `BP_SharedStorageChest` — общее содержимое для всех игроков.
- `BP_PersonalStorageChest` — отдельное содержимое каждого игрока.

У компонента `LinkedStorage` настройте `StorageDefinition`, `StorageAccessMode`,
`WindowClass`, локализуемый `WindowTitle` и допустимую дистанцию `MaxUseDistance`.
Дополнительно действует общая настройка дистанции взаимодействия системы.
У примеров уже назначено существующее окно `WBP_StorageAccess`.
Коллизия меша должна блокировать канал из `Invenza Inventory → InteractionTraceChannel`.
У готовых примеров это настроено; в Example Project используется канал `Interaction`.

В Example Project откройте `/InventorySystemInvenzaPlugin/Maps/Map_Ex`:
на дальней стороне площадки, при Y=1900, размещено по два сундука каждого режима
с подписями `SHARED` и `PERSONAL`. Карта включена в ZIP плагина вместе с
персонажем, GameMode, HUD и необходимыми ресурсами. Откройте её и нажмите Play.
В новой группе выдаётся 3 лозы. Опустошённый инвентарь не получает их повторно.

## Создание собственной группы

1. Создайте Data Asset класса `LinkedStorageDefinition`.
2. Назначьте непустой `StorageGroupID`.
3. В `Inventory.Settings` задайте класс физического инвентаря, вместимость,
   ограничения и существующие классы виджетов. Для сетки задайте число строк и столбцов.
4. При необходимости заполните `Inventory.StartItems`. Все предметы должны помещаться.
5. Назначьте **один и тот же Data Asset** каждому связанному сундуку группы.
6. Выберите режим `Shared` или `Personal` на компоненте сундука.

Разные группы независимы. Одинаковая группа в разных режимах также имеет разные
инвентари. Два разных Data Asset с одинаковым ID группы — ошибка конфигурации:
второй доступ отклоняется. Не меняйте ID группы после создания сохранений;
такое изменение создаёт другую сеть хранения.

Владелец принудительно создаёт физический инвентарь без ссылок на его предметы
и без сбора вместимости из клиентского виджета. Обычный перенос предметов в
рюкзак поддерживается. Начальное наполнение создаётся один раз, в том числе
отдельно для каждого нового личного владельца. Количество сверх размера стака
раскладывается по нескольким стакам; непомещающееся наполнение отклоняется целиком.

## Блокировка всей группы

Открытие общего сундука закрепляет хранилище за одним игроком. Другие игроки не
могут открыть или изменить его через любой сундук той же группы. Блокировка
принадлежит хранилищу, а не отдельному сундуку.

Закрытие окна, уход за допустимую дистанцию, потеря управления персонажем,
отключение игрока и уничтожение открытого сундука освобождают доступ. Запоздалое
закрытие предыдущего владельца не снимает блокировку следующего игрока.

У личного режима блокируется инвентарь конкретного аккаунта. Другие игроки могут
открывать собственные личные инвентари через тот же сундук. Содержимое получает
только соединение игрока с действующим доступом; близость к сундуку или к владельцу
инвентаря сама по себе не даёт права получать данные.

## Постоянный ID личного владельца

Для одиночного режима и локального хозяина listen-сервера предусмотрен ключ
`LocalHost`, ограниченный сохранением текущего прохождения. При наличии сетевого
ID аккаунта из Online Subsystem используется его тип и значение. Система входа
проекта должна подтверждать эти ID на сервере.

Для собственной авторизации или LAN:

1. Добавьте `LinkedStorageIdentityComponent` на `PlayerController`.
2. После успешной серверной авторизации вызовите `SetPersistentPlayerID` с
   постоянным ID аккаунта **до первого открытия личного сундука**.
3. При переподключении назначьте тот же ID новому контроллеру.

Метод работает только на сервере, не является клиентским RPC и допускает назначение
ID один раз. Компонент не реплицирует его клиентам. Имена персонажей и временные
NULL/LAN ID не используются как личность. Удалённый LAN-клиент без назначенного
постоянного ID не откроет личный сундук; общий режим от аккаунтного ID не зависит.

Не выдавайте один ID разным аккаунтам. Передача ID из клиентского поля без
проверки авторизации позволяет представиться другим владельцем и недопустима.

## Сохранение и загрузка

Существующая система сохранения записывает каждый физический инвентарь один раз
по режиму, группе и, для личного режима, ID владельца. Сохраняются также личные
инвентари отключённых игроков и группы, у которых не осталось сундуков.

Загрузка восстанавливает владельцев и предметы, после чего новые точки доступа
находят их по прежнему ключу. Пустой сохранённый инвентарь остаётся пустым.
Блокировки и открытые окна не сохраняются. `ResetPlaythrough` начинает новое
прохождение и сбрасывает оба режима вместе с остальными инвентарями мира.

Данные ограничены текущим миром и профилем сохранения. Перенос одного личного
хранилища между разными картами/серверами требует отдельной аккаунтной системы.

При переносе между хранилищем и другим владельцем экземпляр предмета получает
нового UObject-владельца. Полный перенос сохраняет постоянный ID и пользовательское
состояние; частичный перенос сохраняет остаток в исходном инвентаре. Это позволяет
закрыть сетевой канал сундука, не потеряв предмет, который уже находится в рюкзаке.

## Проверка

Целевой автотест: `Invenza.Storage.LinkedStorage`. Он проверяет идентичность общего
инвентаря, блокировку группы, разделение личных данных, замену контроллера,
дистанцию, сохранение и восстановление. Сетевой стенд проекта отдельно проверяет
репликацию на выделенном сервере и двух клиентах, включая сохранение предмета в
рюкзаке после закрытия сундука; стенд не включается в плагин.
